# Tsundoku — Multi-User Shelf, Google Sheets Storage & Ownership Transfer Specification

## 1. Overview & Architecture Principles

Tsundoku evolves from a single-user ISBN scan + online lookup + LLM enrichment flow into a multi-user application deployed on a single Cloudflare Worker origin (`https://tsundoku.singbaobao.com` in production; `http://localhost:8787` in local development).

### Core Architectural Choices
- **Single-Origin Deployment:** Astro SSR and auth/API routes run together inside the `tsundoku` Cloudflare Worker (`@astrojs/cloudflare/entrypoints/server`), sharing `tsundoku.singbaobao.com` so cookies and OAuth callbacks stay first-party.
- **Sovereign Personal Storage + Thin Coordination Index:** Actual book records live in each user's personal Google Sheet (`drive.file` scope). Cloudflare D1 stores identity, session/account records, encrypted per-user Google Sheets refresh tokens, shelf configuration (`shelf_configs`), and ownership transfer audit logs (`ownership_transfers`).
- **Incremental Google OAuth:** Sign-in OAuth requests basic profile/email only. Connecting or provisioning a personal Google Sheet requests incremental `drive.file` consent separately so sign-in remains lightweight and scoped strictly to user-created or user-selected files.
- **Deferred Package Extraction & Hono Layer:** Keep changes focused inside `apps/tsundoku` during the initial phases. Defer extracting shared workspace packages (`@repo/book-schemas`, `@repo/book-shelf`, `packages/platform/auth`, `packages/platform/connectors/google-sheets`) and introducing a standalone Hono backend layer until core end-to-end workflows stabilize, avoiding speculative boundaries early on.

## 2. Rollout Phases

### Phase 1 — Auth + D1 Foundation
- Better Auth configured in `apps/tsundoku` backed by Cloudflare D1 (`users`, `accounts`, `sessions`, `verifications`).
- Social OAuth (GitHub, Google, Microsoft with `prompt: "select_account"`) and email/password sign-up/sign-in with verification and password-reset flows via Resend.
- `/login` page and protected `/dashboard` route guarded by middleware and server checks.

### Phase 2 — Profile & Personal Google Sheet Binding
- Profile / shelf settings UI allowing an authenticated user to connect a personal Google Sheet (`drive.file` OAuth flow — the only scope requested) and configure `default_visibility` (`private` | `shared`) and `allow_incoming_transfers` (`boolean`).
- Encrypted refresh token storage in D1; a short-lived access token is minted on demand (`GET /api/sheets/token`) for the Picker and Sheets calls, so the refresh token never leaves the server.
- **One-click "Create New Google Sheet":** `POST https://sheets.googleapis.com/v4/spreadsheets` creates the spreadsheet (default `Books` tab + canonical header row) and binds it immediately, since creating the file under `drive.file` grants the app access to it.
- **"Browse Google Drive" via the Google Picker API:** a `google.picker.ViewId.SPREADSHEETS` modal (public `GOOGLE_PICKER_API_KEY` plus an optional project number for `setAppId`) lets users select an existing sheet without pasting a raw URL; on `Action.PICKED` the app reads the file's tabs via `spreadsheets.get`, defaults to the first tab or lets the user choose, then binds it (`shelf_configs`).
- Clear re-authorization prompting when the stored grant is missing, expired, revoked, or lacks `drive.file` access to a file, instead of a generic "not found" error.
- Updating the scan/save workflow so scanned and enriched books write to the signed-in user's personal Google Sheet rather than ephemeral state.

### Phase 3 — Dashboard Tables (Own + Shared)
- **My Shelf (`OWNER`):** Read rows from the signed-in user's linked Google Sheet (`spreadsheet_id` + `sheet_tab_name`), mapping the canonical columns (`isbn13`, `title`, `authors`, `publisher`, `publishedYear`, `summary`, `source`, `verified`, `enriched`, `confidence`, `visibility`, `ownerEmail`, `addedAt`, `transferredFrom`) into typed items keyed by their 1-based spreadsheet row. Edit the user-editable fields (`title`, `authors`, `publisher`, `publishedYear`, `summary`, and `visibility` between `private`/`shared`) and delete rows.
  - `GET /api/shelves/own` returns the `OwnShelfView` (`empty` / `not_connected` / `unlinked` / `ok` / `error`).
  - `PATCH /api/shelves/own/rows` re-reads the target row and overlays the editable fields (preserving provenance columns), then writes it back.
  - `DELETE /api/shelves/own/rows` removes a row with `spreadsheets.batchUpdate` → `deleteDimension` keyed on the tab's numeric `sheetId`, so remaining row indices stay consistent.
  - The dashboard shows the human-readable sheet title alongside the tab (`"<Sheet Title> (tab: <sheet_tab_name>)"`) while `spreadsheet_id` remains internal, and renders clear empty, unlinked, and re-consent (missing/revoked refresh token) states.
- **Shared Shelves (`VIEWER`, read-only):** Query D1 for other users' `shelf_configs` where `spreadsheet_id IS NOT NULL`, `sheet_visibility = 'shared'` (Phase 6 — the dedicated sheet-level flag, independent of `default_visibility`), and a refresh token exists. Each shared sheet is fetched on the server using its owner's decrypted token (with on-demand token refresh); rows explicitly marked `private` are filtered out.
  - `GET /api/shelves/shared` returns the read-only shared views; each shelf is isolated so one owner's revoked/invalid token surfaces as a single error card without failing `/dashboard`.
  - Reads are cached in KV (`SHELF_CACHE`, 60s TTL) when the binding is present, with a safe no-KV fallback when it is unbound.
  - A shelf selector in `/dashboard` switches between My Shelf and each shared shelf. No edit, delete, or transfer surface is exposed for shared shelves in either the UI or the endpoints.
  - **Phase 5 Group Alignment:** In Phase 5, shared-shelf discovery, row visibility, and aggregation are extended by the three-level visibility model (group membership → sheet-level `shared`/`private` → row/item-level group targeting across zero, one, or multiple groups), aggregating eligible shared items across all active groups with a multi-select group filter.

### Phase 4 — Ownership Transfer
- **Target-Owner Selector & Eligibility:** Populate the target-owner selector from eligible recipients (`allow_incoming_transfers = true` and a configured Google Sheet). In Phase 5, eligibility is further scoped to active members who share at least one group with the sender.
- **Two-Step Append-Then-Remove Workflow:**
  1. Verify caller ownership of the source item/row and verify target-owner eligibility (linked sheet, incoming transfer flag, and group overlap once Phase 5 is active).
  2. Append the item (recording `transferredFrom` and the new `ownerEmail`) to the recipient's Google Sheet.
  3. Remove or mark the item (`TRANSFERRED`) in the sender's Google Sheet only after step 2 succeeds so a failed append never silently drops a book.
  4. Write an audit record to D1 `ownership_transfers` capturing transfer details and outcome.
  

### Phase 5 — Groups & Scoped Sharing / Transfers
- Add user-created groups with privacy-preserving onboarding (exact-email in-app invitation acceptance panel and/or expiring invite codes without public user directories). 
- Scope shared-shelf visibility and ownership-transfer target selection to active members of the same group, backed by D1 tables for groups, memberships, and invitations.

5. **Phase 5 — Groups, Token Invitations & Three-Level Visibility / Transfers:**
   - **Group Creation & Invite Tokens (No Public Directory):** Any authenticated user can create a named group and becomes its `admin`. Each group has an active invite token/link targeting `https://tsundoku.singbaobao.com` (e.g., `?invite=<token>`). The admin can regenerate the token at any time, immediately invalidating prior tokens for new join attempts while keeping existing members active. No public user or group directory is exposed.
   - **Token Preservation Across Sign-In:** Opening an invite link while signed out preserves the token across authentication redirects (OAuth or email login) and presents the invitation once authenticated.
   - **Invitation States (`Accept`, `Ignore`, `Remove`):**
     - **Accept:** Adds the signed-in user as an `active` group member and marks the invitation `accepted`.
     - **Ignore:** Marks the invitation `ignored` so it is hidden from active/unread prompts without joining the group, while remaining accessible if the user views ignored invites before token rotation.
     - **Remove:** Marks the invitation `removed` and clears it from the user's invitation list; reusing the same token after removal is rejected unless a new token is issued or the admin re-invites.
   - **Three-Level Visibility Model (Membership -> Sheet -> Row/Item):**
     - **Group Membership:** Sharing and ownership transfers apply only among `active` members of a group.
     - **Sheet Level:** A member's linked Google Sheet is either `private` (not shown to other group members as a shared shelf) or `shared` (shown as a shared shelf to group members, even when zero rows are visible to the viewer).
     - **Row / Item Level:** Row visibility applies only when the owner's Google Sheet is `shared`, and can be associated with zero, one, or multiple groups. A row is visible to a viewer only when the owner's sheet is `shared` and the row's target groups intersect with a group shared by both the owner and the viewer (with the viewer still being an `active` member).
   - **Shared Shelves Aggregation & Multi-Group Filter:** Shared Shelves aggregate eligible shared books across all of the signed-in user's active groups and provide a group filter supporting multiple group selection.
   - **Group-Scoped Ownership Transfers:** Ownership transfer targets (Phase 4) are restricted to `active` members who share at least one group with the sender and have a valid linked shelf with incoming transfers enabled; transfers continue to write a D1 audit record.
   - **Server-Side Enforcement:** Group membership, sheet visibility, and row-level group matching are enforced on the server when reading shared shelves or executing transfers, while honoring owner Google Sheet token health.

### Phase 7 — User-Controlled LLM Enrichment
- **ISBN Scanner preference:** The home page (`/`) exposes an `Enrich book info with LLM` radio group (`Yes` / `No`), server-rendered from the signed-in user's saved preference and disabled for anonymous visitors. Toggling it persists immediately via `POST /api/shelves/enrich-setting` (`{ enrichWithLlm: boolean }`), stored on `shelf_configs.enrich_with_llm` (integer `0`/`1`, default `0` = "No", so enrichment is opt-in). A failed save reverts the radio to the last server-confirmed value.
- **Scan gating:** When the preference is `No`, an ISBN scan performs only the fast catalog lookup (Open Library → Google Books) and skips the Featherless call entirely. When `Yes`, the existing catalog-first + Featherless enrichment flow runs (still best-effort and graceful). The lookup route re-reads the preference server-side on each request, so a toggle takes effect on the next scan without a page reload; anonymous visitors and D1 read failures default to no enrichment.
- **"Batch action" in My Shelf:** A `Batch action` sub-section sits directly between the Linked Sheet / Sheet Visibility block and the book records table, containing an `Enrich info of all books with LLM` button that is disabled when no sheet is linked or while a job is running, and shows an `Enriching…` busy state.
- **Bulk enrichment flow (`POST /api/shelves/batch-enrich`):** Read every row from the linked sheet and select only rows that have a valid ISBN **and** a blank `summary`; rows with an existing or hand-edited summary are skipped and never overwritten. The unenriched books are sent to Featherless in bounded chunks (`BATCH_CHUNK_SIZE = 25`) as one structured prompt per chunk returning `{"summaries":[{"key","summary"}]}`, keyed by spreadsheet row index so two rows sharing an ISBN never collide. Returned summaries are written back into the `summary` column in a single `values:batchUpdate` (each range targeting only the `summary` cell), the shared-shelf cache is invalidated, and the table refreshes in place. Nothing is written until every chunk succeeds, so a failed chunk (`502 UPSTREAM_ERROR`) is fully recoverable.

### Phase 8 — Cover Vision ("Read Book Title") Mode & Three-Tier Entitlements
- **Three user tiers (single source of truth `src/lib/entitlements.ts`):**
  1. **Free-Unregistered** (`!session.userId`): anonymous and stateless — every book lives in client state (`localStorage`), never in D1. Allowed: `Scan ISBN` barcode lookup and manual title/author catalog search. No AI features.
  2. **Free-Registered** (`session.userId`, no remaining credit): signed in and D1-backed (personal shelf, groups, memberships). Allowed: `Scan ISBN`, manual title/author search, and every D1 shelf/group feature. No AI features.
  3. **Paid-Registered** (`session.userId` **and** a positive credit balance): signed in with remaining USD credit from a **$0.99 HitPay top-up** (Phase 10). Everything in Free-Registered **plus** both AI features — book summary enrichment via `FEATHERLESS_MODEL` (`Qwen/Qwen2.5-7B-Instruct`) and cover title reading via `FEATHERLESS_VISION_MODEL` (`Qwen/Qwen2.5-VL-7B-Instruct`) — each deducting its configured per-action credit rate.
- **Positive balance = unlocked:** the legacy boolean `shelf_configs.has_llm_unlock` is superseded by a derived credit balance (`credit > 0` = AI unlocked). `readShelfEntitlement(db, userId)` in `src/lib/llm-entitlement.ts` returns `{ hasLlmUnlock, enrichWithLlm, creditBalance }`, where `hasLlmUnlock` is computed as `balance > 0` and every read fails **closed** (locked) on a missing row, unapplied migration, or D1 error. AI routes fall back to `balance: 0` when they read the entitlement directly, so "sufficient credit" and "unlock" are never two different numbers.
- **Server-side enforcement:** `enforceAiAccess({ userId, hasLlmUnlock })` gates every AI route *before* it touches Featherless, returning `401 UNAUTHENTICATED` (anonymous) or `403 LLM_LOCKED` (signed in, no remaining credit). Gated routes: `POST /api/books/extract-cover`, `POST /api/shelves/batch-enrich`, and `POST /api/shelves/enrich-setting`; `POST /api/isbn-lookup` enriches only when the caller is signed in, has credit, **and** has the `enrich_with_llm` preference on. Every gate fails closed on a D1 read error, so a free tier can never reach the LLM.
- **Scanner mode switch (three modes):** `/` shows a **Mode** radio group — **`Scan ISBN`** (default; **auto-starts** the live camera and runs **continuous** barcode detection → `POST /api/isbn-lookup` → catalog → save, across all three tiers), **`Enter Book Title`** (manual title/author catalog search for books without a scannable barcode), and **`Read Cover with AI`** (Paid-Registered cover-vision capture, also auto-started). Selecting a mode swaps its panel and releases the previous mode's camera tracks; only one camera ever runs at a time, and the main page heading (`#page-heading`) tracks the active mode (`ISBN Scanner` / `Manual Entry of Book Title` / `Read Title from Book Cover by AI`). Each mode keeps its **own** `Match found` card and **All Possible Book Titles** list — a switch shows **only** the active mode's results (the others are hidden, not discarded, and reappear untouched when the user switches back). Each mode also owns its own instructional/status bar, placed inside its panel: directly **below the camera viewfinder** in `Scan ISBN` and `Read Cover with AI`, and **above the "No barcode? …" hint** in `Enter Book Title`.
- **`Scan ISBN` — auto-start + continuous scanning:** on initial load (as the default) and whenever the mode is selected, the page calls `navigator.mediaDevices.getUserMedia` (`facingMode: { ideal: "environment" }`, `audio: false`) **without** a "Start Camera" step; there is no manual **Start/Stop/Scan Frame** control in the active state. A continuous loop decodes frames (`BarcodeDetector` when available, `@zxing/browser` `BrowserCodeReader` otherwise) and, on each **newly detected** ISBN (one that differs from the code already in the input, so the same in-view barcode never re-fills or clobbers typing), writes the normalized ISBN-13 into **Manual ISBN** and turns **Look up** green — the loop never pauses, so scanning stays uninterrupted. The user taps **Look up** to resolve the number into `Match found` (there is **no** separate "Scan Next" step). A denied permission or a `getUserMedia` failure shows a clear error with a **Retry Camera** button (which restarts the stream), instead of silently failing.
- **`Enter Book Title` — manual catalog search (all tiers):** renders stacked (never side-by-side) **Title** (required) and **Author (optional)** inputs plus a **Search** button and a **Just Save It** button. **Search** posts `POST /api/title-lookup` (`{ title, author? }` → `{ editions }`) — Open Library `search.json` first, then Google Books (`intitle:`/`inauthor:` refined, then a plain `q=` free-text fallback so multi-word/symbol/Chinese titles resolve reliably) — and renders the best matching edition straight into this mode's read-only **`Match found`** card (`confidence: "high"` when the edition carries an ISBN, `"medium"` otherwise) **and** populates this mode's own **All Possible Book Titles** list from the returned `editions` (mirroring `Read Cover with AI`, so ambiguous manual searches can be disambiguated the same way); an empty result shows a clear no-match message inviting a retry. **Just Save It** renders the typed title/author as a user-confirmed manual entry in the same `Match found` card with provenance `Source: manual entry · not verified · not enriched · Confidence: high` (and clears the stale candidate list).
- **`Read Cover with AI` (Paid-Registered only):** selecting the mode **opens the live camera immediately** (no separate trigger button), mirroring `Scan ISBN`. It uses `navigator.mediaDevices.getUserMedia` (preferring the rear/`environment` lens where supported) with a single **Capture** control; pressing **Capture** grabs the current frame to an offscreen `<canvas>`/blob and runs the cover pipeline in one step — **without** calling `track.stop()`, clearing `video.srcObject`, or unmounting/hiding the `<video>`, so the live viewfinder keeps streaming during the read and after `Match found` is shown and the user can immediately re-frame and capture again. There is **no intermediate "Use photo" / "Retake" confirmation**; **Capture** is disabled only while the request is in flight (with a `Reading cover…` status), then re-enabled. The OS file picker is used **only as a fallback** when the camera is unsupported, permission is denied, or no device is present. Free-Unregistered and Free-Registered users are prompted to sign in / unlock for **$0.99** instead of calling the endpoint. For Paid-Registered users the frame is down-scaled on the `<canvas>` (longest edge ≤ 1024 px, JPEG quality `0.8`) and posted to `POST /api/books/extract-cover`.
- **"All Possible Book Titles" disambiguation (both `Read Cover with AI` and `Enter Book Title`):** after a catalog query — a cover capture via `POST /api/books/extract-cover`, or a manual search via `POST /api/title-lookup` — the best result renders into that mode's read-only `Match found` card, while the returned candidate editions (`extract-cover`'s `candidates`, `/api/title-lookup`'s `editions`) populate an **All Possible Book Titles** list inside the same mode's panel, headed `All Possible Book Titles` with the helper line `Edit a row and tap Select to use that book instead.` Each row has editable **Title** / **Author (optional)** / **ISBN (optional)** inputs (reusing the exact same `field-input` styling as the **Manual ISBN** box) plus a **Select** button (reusing **Look up**'s `field-button` styling); when the catalog resolved nothing, a single row is seeded from the raw hint (the extracted cover text, or the typed title). On **Select**, a provided ISBN wins (canonical `POST /api/isbn-lookup`, which also applies the caller's LLM-enrichment preference server-side); otherwise the row's `Title` + `Author` are searched via `POST /api/title-lookup` and the best edition (preferring a canonical ISBN lookup when it carries one) updates that mode's read-only `Match found`. An empty/invalid combination or a no-match shows the ephemeral message `"That is not a valid combination. Check the combination and try again."` (styled like the invalid-ISBN message), which clears on the next successful lookup or the next capture.
- **`POST /api/books/extract-cover` (Paid-Registered only) — complete single-pass pipeline:** accepts `{ image }` — a base64 JPEG/WebP `data:` URL, rejected with `413 PAYLOAD_TOO_LARGE` above 1 MB and `400 INVALID_REQUEST` for a non-image/bad MIME. It sends an OpenAI-compatible multimodal `chat/completions` request (`content: [{ type: "text" }, { type: "image_url", image_url: { url } }]`) to `FEATHERLESS_VISION_MODEL` (default `Qwen/Qwen2.5-VL-7B-Instruct`). The vision output is a **hint, not ground truth**: the grounded prompt combines a multi-line display title into one coherent clause (`"The $100"` / `"Startup"` → `"The $100 Startup"`), reads English and Chinese (Simplified & Traditional) covers, keeps a secondary line in `subtitle`, and **returns an author only when the name is clearly legible on the cover — an empty array otherwise — never guessing from prior knowledge, the title, or the topic**; `publisher`/`isbn` are likewise `null` unless clearly visible. The `title`/`isbn` hints then query the catalog (`lookupByIsbn` when a valid ISBN is legible, else `searchEditions` by title; a vision title carrying the author's name as a possessive prefix — e.g. `"Chris Guillebeau's The $100 Startup"` — has the prefix stripped, only for the already-extracted author, and the cleaned title is tried as a second candidate); a hit promotes canonical `title`/`authors`/`publisher`/`isbn` over the vision guesses (the vision `subtitle` is kept, since no provider supplies one). When a catalog match resolved a valid ISBN **and** the caller's `enrich_with_llm` preference is on, the same request then applies the best-effort Featherless summary enrichment (deducting `CREDIT_RATE_BOOK_SUMMARY`) so the response is the **finished** record. The route is the **single source of truth** for a cover read: the client performs **no follow-up lookup** after it returns. The strict `200 OK` body is `{ title, subtitle, authors, publisher, publishedYear, isbn, summary, enriched, source, provider, confidence, candidates }`, where `source` is `"catalog_lookup"` (a catalog match resolved the details — `provider` names the catalog, `confidence: "high"`) or `"vision_only"` (no match, or the catalog was unavailable — `provider: null`, `confidence: "low"`; a catalog error degrades silently instead of failing the read), and `candidates` is a `CatalogEdition[]` — the catalogue editions behind the match (or `[match]` when resolved from an ISBN hint, `[]` for a vision-only read) that the client renders as the **All Possible Book Titles** rows. Each read logs `source`, the `title`/`isbn` hints, and the resolved fields server-side for diagnosis. Failures return `502 UPSTREAM_ERROR`; a missing key returns `503 CONFIG_ERROR`.
- **Scanner layout:** the unnamed scanner section groups the **Mode** radio group (`Scan ISBN` / `Enter Book Title` / `Read Cover with AI`) together with the **`Enrich book info with LLM`** (`Yes` / `No`) radio group, the latter sitting directly below **Mode** so both controls read as one block; there is no separate "AI features" panel.
- **`Match found` result (read-only, scoped per mode):** each of the three scanner modes owns an **independent** `Match found` container (alongside its own status/loading state), so switching modes shows **only** the active mode's card — the others are hidden, not discarded, and reappear untouched when the user switches back. The heading is always the plain **`Match found`** (the per-mode scoping comes from rendering into that mode's own container, not from the heading text). Any resolved book renders as a **non-editable** card (users who want to edit switch to `Enter Book Title`), showing title/author/publisher/year/summary, an optional `ISBN-13`, the provenance line, and a **Save** action — no second query and no intermediate catalog/ISBN screen. The primary action buttons (**Save to my shelf** / **Save on this device** and **Select**) reuse the same `field-button` rule as **Look up** / **Search** / **Just Save It** (same padding, border radius, weight, height, border/fill, and hover/active states), with `.action-button` only adding full width for buttons outside a stretched `.controls` flex row; text fields reuse the shared `field-input` rule.
- **No-match fallback & manual entry (all tiers):** a `Scan ISBN` miss shows a clear no-match/error message and clears the stale card; an `Enter Book Title` search with no editions shows a clear message inviting a retry or **Just Save It**; a `Read Cover with AI` read that reports `vision_only` renders the grounded vision hints into `Match found` (unverified, `confidence: "low"`) alongside a status noting no catalog match was found. A user-confirmed manual entry is a `SaveableBook` (`source: "manual"`, `verified: false`) with a synthetic `manual:<slug>-<hex>` id in the `isbn13` slot; **Just Save It** marks it `confidence: "high"` (user-confirmed), whereas a vision-only cover read keeps `confidence: "low"`. Free-Unregistered users keep it in `localStorage` (stateless — no D1 write); Free-Registered / Paid-Registered users persist it through `POST /api/sheets/save-book`.
- **Saveable-book contract:** `SaveableBook` is a superset of the ISBN-path `BookLookupResult` (its `source` enum extends to `"manual"`), so the ISBN scan path, the manual title-lookup path, and the cover-vision path share a single save route; synthetic ids are not valid ISBNs, so catalog-only flows (lookup, batch enrichment) naturally skip them.

### Phase 9 — HitPay Checkout & Webhook Fulfillment for the $0.99 AI Credit Top-Up
- **Single-source entitlement helper (`src/lib/llm-entitlement.ts`):** every read and write of the AI entitlement goes through this module so the UI gate, the AI API routes, and payment fulfillment always agree on the exact same state. It exposes `readShelfEntitlement(db, userId)` (`{ hasLlmUnlock, enrichWithLlm, creditBalance }`, where `hasLlmUnlock = creditBalance > 0`, failing **closed** to all-`false`/`0` on a missing row or a D1 read error), `isLlmUnlocked(db, userId)`, and the reference helpers `buildUnlockReference(userId, nonce?)` / `parseUnlockReference(value)` using the `llmunlock:<userId>[:<nonce>]` prefix. The credit ledger itself lives in `src/lib/credits.ts` (Phase 10). Existing AI routes (`extract-cover`, `batch-enrich`, `enrich-setting`, and the enrichment step inside `isbn-lookup`) read the entitlement through this helper instead of ad-hoc `getShelfConfig`/balance calls.
- **`POST /api/shelves/checkout` (signed-in only):** creates a HitPay payment request via `POST ${HITPAY_API_URL}/payment-requests` with header `X-BUSINESS-API-KEY: <HITPAY_API_KEY>`. Body carries `amount` (`LLM_UNLOCK_PRICE_USD` = `0.99`), `currency` (`LLM_UNLOCK_CURRENCY` = `USD`, overridable by `HITPAY_CURRENCY`), `reference_number` = `llmunlock:<userId>:<nonce>` (a per-payment nonce keeps each reference unique, as HitPay requires), `redirect_url` back to the caller's return path (`/?unlock=return&ref=<reference>` by default; the optional JSON body field `returnTo` selects `/settings` for the Account Settings top-up button, sanitised to a same-origin bare path so it can never redirect off-origin), and the app's webhook URL. Top-ups are **repeatable**: a caller who already holds credit is charged again (there is no `alreadyUnlocked` short-circuit — the UI keeps the "Top up AI credits" button available at any balance). The pending payment is persisted best-effort via `recordPendingPayment` (keyed by payment id + unique reference) so a return can reconcile it even if the deprecated per-request webhook never fires. Returns `{ ok: true, url, referenceNumber, currency, amount }`; anonymous callers get `401 UNAUTHENTICATED`, missing config `503 CONFIG_ERROR`, and upstream failure `502 UPSTREAM_ERROR`.
- **`POST /api/shelves/reconcile-payment` (signed-in only):** the return-time confirmation path. Loads the pending `credit_payments` row by `reference`, rejects a reference whose embedded user id is not the caller (`403 FORBIDDEN`), and confirms the payment's real state via HitPay's `GET /payment-requests/{id}`. A confirmed `completed` payment whose amount (within a `0.001` epsilon) and currency match credits the ledger **idempotently** (unique reference) and returns `{ ok: true, status: "completed", credited: <boolean>, balance, amount }`; a mismatch is recorded as `failed` (`{ status: "failed", reason: "amount_mismatch" }`); a still-processing payment returns `{ status: "pending" }`; a missing row returns `{ status: "unknown" }`; and a HitPay lookup failure returns `502 UPSTREAM_ERROR`. Already-`completed` rows are re-confirmed idempotently without a second HitPay call.
- **`POST /api/webhooks/hitpay` (signature-verified, idempotent):** verifies the `Hitpay-Signature` header as HMAC-SHA256 of the **raw** request body keyed by `HITPAY_SALT` (constant-time compare) **before** trusting any field. A missing salt returns `503 CONFIG_ERROR`, an invalid signature `401 UNAUTHENTICATED`, and a non-JSON body `400 INVALID_REQUEST`. Non-`completed` statuses, foreign/unknown references, and amount/currency mismatches are acknowledged with `{ ok: true, ignored: true }` and never credit. A verified `completed` payment for a `llmunlock:<userId>` reference whose amount matches `LLM_UNLOCK_PRICE_USD` (within a `0.001` epsilon) and currency matches `LLM_UNLOCK_CURRENCY` calls `addCredit` (idempotent on the reference) and returns `{ ok: true, credited: <boolean>, balance }`; a failed D1 write returns `500` so HitPay retries. Replayed/out-of-order deliveries are safe because the credit insert is `INSERT OR IGNORE` on a unique reference.
- **`GET /api/shelves/entitlement` (client refresh):** returns `{ signedIn, hasLlmUnlock, enrichWithLlm, creditBalance }` for the caller (`signedIn: false`, locked flags, and `creditBalance: 0` when anonymous), so the scanner can re-read the balance after the HitPay redirect.
- **Return flow:** both `/` and `/settings` read the ledger server-side on load. When the URL carries `?unlock=return&ref=<reference>` and the user is signed in, the client calls `POST /api/shelves/reconcile-payment` with that reference a few times (short interval), falling back to a direct `GET /api/shelves/entitlement` balance read, to pick up a webhook/settlement that lands slightly after the browser redirect. A confirmed payment shows a **one-time ephemeral** success status (`Payment of $0.99 is successful. AI credit remaining: $<balance>.`) that is **not persisted** — the banner is never server-rendered into the page and is un-hidden only by this live return/confirmation path, so a later reload never re-shows it (see Phase 10 scanner display); a pending/failed/unknown outcome is surfaced explicitly; then the `unlock`/`ref` query params are stripped.

### Phase 10 — Credit Metering & Billing Visibility
- **Credit ledger (`src/lib/credits.ts`):** AI access is funded by a USD-denominated, append-only balance rather than a one-time boolean. `credit_ledger.amount` is **signed** — top-ups are positive, usage is negative — so the remaining balance is simply `SUM(amount)` and "added"/"used"/"remaining" are auditable sums, never guessed counters.
- **Per-action credit rates from bindings (`resolveCreditRates(bindings)`):** each rate is read from a Worker binding (`.dev.vars` / Cloudflare vars+secrets) and falls back to a documented default when unset, blank, or invalid. The three `CREDIT_RATE_*` bindings and defaults:
  - `CREDIT_RATE_BOOK_SUMMARY` (default `0.00001`) — per single book summary.
  - `CREDIT_RATE_BATCH_BOOK_SUMMARY` (default `0.00010`) — per book inside a batch summary run.
  - `CREDIT_RATE_BOOK_TITLE_IMAGE` (default `0.00005`) — per book title / cover-image extraction.
- **Accurate, recorded deductions:** every AI action records a negative ledger event (`recordUsage`) with its resolved per-action amount, so metering is auditable rather than inferred:
  - **Single book summary** — `POST /api/isbn-lookup` deducts `CREDIT_RATE_BOOK_SUMMARY` when it runs the LLM summary step.
  - **Batch summary** — `POST /api/shelves/batch-enrich` deducts `CREDIT_RATE_BATCH_BOOK_SUMMARY` per book actually enriched.
  - **Cover / title image** — `POST /api/books/extract-cover` deducts `CREDIT_RATE_BOOK_TITLE_IMAGE` per cover read (via its injectable `chargeUsage` → `meterUsage` helper).
  A zero/negative configured rate records no row (nothing to meter). Metering is best-effort and never fails the underlying AI response.
- **Settings "Billing & Metering" (`/settings`):** `getCreditSummary(db, userId)` returns `{ totalAdded, totalUsed, balance, usageByAction[] }` (usage grouped by action, largest first, with human labels), and `resolveCreditRates(env)` surfaces the current per-action rates. The page shows **Total credit added**, **Current credit remaining**, **Total usage** (with a per-action breakdown), and the **current per-action rates**. It also carries a **"Top up AI credits — $0.99"** button that is always visible and enabled **regardless of the current balance**, so the user can top up again at any time; the button posts `POST /api/shelves/checkout` with `{ returnTo: "/settings" }` and, on return, the reconcile flow shows `Payment of $0.99 is successful` plus the refreshed figures in place (no reload).
- **Scanner display (`/`):** the entitlement is resolved server-side on load. **`Unlock AI features for $0.99`** is shown **only** when the remaining credit is `0` (or the user has never unlocked/topped up) and the user is signed in; at any positive balance it is hidden entirely. The success banner `Payment of $0.99 is successful. AI credit remaining: $<balance>.` is rendered **hidden** server-side and is **ephemeral** — it is un-hidden **only** by the live top-up confirmation path (the `?unlock=return` reconcile poll or the entitlement re-read that observes an increased balance), never on first paint or a reload, so it appears exactly once right after a successful top-up and never persists. The dashboard's top-right button is labelled **"Account settings"** and links to `/settings`.
- **Legacy migration:** migration `0008` (below) backfills a one-time `0.99` top-up for users previously holding the boolean `has_llm_unlock`, so existing paid users keep access under the credit model.

## 4. Security & Operational Requirements
- `trustedOrigins` in Better Auth must include `http://localhost:8787`, `http://127.0.0.1:8787`, and `https://tsundoku.singbaobao.com`.
- AI-backed routes (`POST /api/books/extract-cover`, `POST /api/shelves/batch-enrich`, `POST /api/shelves/enrich-setting`, and the enrichment step inside `POST /api/isbn-lookup`) resolve the caller's tier server-side and must fail closed — a free tier never reaches Featherless, even if the D1 read fails.
- `FEATHERLESS_API_KEY`, `FEATHERLESS_MODEL` (text summaries, default `Qwen/Qwen2.5-7B-Instruct`), and `FEATHERLESS_VISION_MODEL` (cover reading, default `Qwen/Qwen2.5-VL-7B-Instruct`) are read only server-side in the Worker and are never exposed to `src/pages/index.astro`, client scripts, error messages, or logs.
- `HITPAY_API_KEY`, `HITPAY_SALT`, and `HITPAY_API_URL` are Worker secrets (dev values in `.dev.vars`) read only server-side; `HITPAY_CURRENCY` (optional, defaults to `USD`) overrides the unlock currency. `POST /api/webhooks/hitpay` must verify the `Hitpay-Signature` HMAC-SHA256 over the raw body using `HITPAY_SALT` before acting on any payload, and credit fulfillment (`addCredit`) must be idempotent on the unique payment reference.
- `CREDIT_RATE_BOOK_SUMMARY`, `CREDIT_RATE_BATCH_BOOK_SUMMARY`, and `CREDIT_RATE_BOOK_TITLE_IMAGE` are Worker vars/secrets (dev values in `.dev.vars`) read only server-side via `resolveCreditRates(env)`; each defaults (`0.00001` / `0.00010` / `0.00005`) when unset, blank, or invalid. AI usage is deducted from the positive `credit_ledger` balance, and a positive balance is the sole gate for the paid AI tier.
- Never log raw OAuth tokens, refresh tokens, or encryption keys.
- Encrypt Google refresh tokens at rest before writing to D1 using a dedicated Worker secret encryption key.
- Only a short-lived access token is ever exposed to the browser (`GET /api/sheets/token`, served `no-store`); the refresh token stays encrypted at rest and is never sent to the client.
- `GOOGLE_PICKER_API_KEY` and `GOOGLE_CLOUD_PROJECT_NUMBER` are public values rendered into `/settings` for the browser Picker — restrict the key by HTTP referrer in the Google Cloud console rather than treating it as a Worker secret.
- Shared-shelf reads never expose another user's credentials to the browser: the owner's refresh token is decrypted server-side and only the mapped rows are returned. The optional `SHELF_CACHE` KV binding (60s TTL) caches those reads; when it is unbound the dashboard degrades to live reads without error.
- Handle Google Sheets API rate limits and transient network errors cleanly with explicit user-facing status feedback.
